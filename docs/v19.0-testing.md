# ZoneMinder v19 acceptance crosswalk

The v19 appliance installs the official ZoneMinder 1.38.4 Trixie package at an exact version and SHA256 digest. The source record retains the package URL, digest, repository channel, and signing-key fingerprint.

`tests/v19.sh` checks the normal appliance path: authenticated HTTPS web and API login with the firstboot application password, including ZoneMinder's intermediate browser post-login session step and a cookie-preserving request to the authenticated Options page; creation and API readback of one non-hardware monitor; an authenticated enable-state update; MariaDB readback; persistence after a ZoneMinder restart; authenticated API deletion; and API/database absence after cleanup. It also checks Apache, MariaDB, ZoneMinder, and Postfix service state, the Adminer and Webmin HTTPS endpoints, and the supervised stable-channel updater.

## Exact-run status

The first three exact Wave 2 executions built, imported, and completed firstboot/runtime health successfully. The first web-login check stopped on ZoneMinder's JavaScript-driven intermediate post-login page. The second preserved the authenticated cookie but requested the console, which ZoneMinder 1.38.4 correctly redirects to its mandatory first-login privacy page while `ZM_SHOW_PRIVACY` is set. The test now requests `?view=options`, an authenticated view that the upstream privacy gate explicitly exempts, and checks its stable `optionsContainer` marker without accepting or changing the privacy choice. That web flow passed in the third execution, which then exposed a monitor-fixture default-field issue: the API hydrated an invalid device default when `Device` was omitted. The fixture now sends the explicit empty value accepted by the exact 1.38.4 validator for its non-local FFmpeg monitor. All three failures are test-only defects and consume no product loop. An exact retry is pending on the isolated Wave 2 builder.

The second retained failure bundle has a harness bookkeeping defect: its top-level `SHA256SUMS` names an omitted `failure-status.txt`. The retained-artifact manifest `RETAINED-SHA256SUMS` fully covers the artifacts that were copied into the bundle (manifest SHA256 `7584085ef063d2bbb25200d5e59bef315fb45441df55df0a8e71f738b572f68e`), and `report.txt` plus `run.log` preserve the run identity, source commit, failure stage, and cleanup result. The evidence is therefore usable even though the top-level manifest cannot validate the omitted file.

The third retained failure bundle's `RETAINED-SHA256SUMS` validates every retained artifact (manifest SHA256 `61339fa0fd8c5a23ab1a01e772a4b27f1ffb5b5013130aee0f9be450b5d60659`). Its report records source commit `faca2b9f7880182d60eebd8c2562f7472effed97`, source archive SHA256 `26ddf16083cd87277d0bec1e032fa24a4d051d6fed30381133122a8da2e33919`, pinned harness identity, the runtime-test failure stage, and successful cleanup/identity/disk checks.

## Deferred boundaries

Camera capture and motion detection require hardware or a representative media stream, so the bounded acceptance fixture uses a disabled FFmpeg monitor. The test proves authenticated monitor management without claiming hardware capture coverage.
